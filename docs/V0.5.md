# Phasecraft v0.5: Bound, Resumable Workflows

The v0.5 runtime and workflow are shared by OpenCode, Claude Code, Codex, and Pi. The installer generates each adapter from the canonical workflow; no separate host implementation of the approval or feedback contract is needed.

## Interactive HTML Planning

1. Run `/phasecraft-plan --work PAY-142`, or `$phasecraft-plan --work PAY-142` in Codex.
2. The planner writes authoritative Markdown, validates it, generates `plan.html` and `roadmap.html`, and opens the plan in the authenticated local review page.
3. Enable **Comment mode**. Comment on a requirement, proposed change, flow, task, risk, or selected text within one review anchor. Drafts are autosaved privately.
4. Choose **Publish feedback**. The server records an immutable `FB-NNN` response with exact Markdown/HTML hashes and a complete reviewable Markdown projection.
5. Copy the returned planner command. Codex receives `$phasecraft-plan --work PAY-142 --feedback FB-NNN`; OpenCode, Claude Code, and Pi receive `/phasecraft-plan --work PAY-142 --feedback FB-NNN`.
6. The planner reads the response through `feedback-show`, independently checks technical claims, dispositions each comment, records the resolution, regenerates HTML, and opens the revised review.

The generated HTML file remains a deterministic derivative. Comments are submitted through its local review server, rather than attempting to write local files from a `file://` page. Publishing does not start an agent automatically. The response remains available after the browser closes or a host changes.

The runtime infers the host from its installed path, including development symlinks. When using the source/package runtime directly, select the host explicitly:

```bash
node bin/phasecraft.mjs runtime review-start --work PAY-142 --host codex --no-open
node bin/phasecraft.mjs runtime feedback-list --work PAY-142 --host codex --pending
node bin/phasecraft.mjs runtime feedback-show --work PAY-142 --host codex --feedback FB-001
```

`PHASECRAFT_NO_BROWSER=1` also disables browser launch. The returned loopback capability URL still opens the interactive page. A standalone plan may render pinned Mermaid diagrams; authenticated review blocks artifact scripts and retains readable Mermaid source.

## Runtime Approval Receipts

After the auditor records `PLAN-VERIFICATION.md` and the human's dispositions, it runs:

```bash
phasecraft runtime approve-plan --work PAY-142
```

The runtime validates the active plan's structural schema, exact HTML source binding, audit outcome, integrity/execution gates, finding-to-Q&A coverage, resolved dispositions and their plan hashes, safe file scope, task dependencies, and commit groups. Semantic warnings remain human-dispositionable; explicit no-guardrail risk acceptance remains valid.

The receipt binds plan, HTML, audit, and evidence-registry hashes plus phase/version, tasks, files, groups, messages, and dispositions. A read-only receipt is saved under `.phasecraft/.local/work/<key>/approvals/P-NN/<fingerprint>.json`, and the authoritative state records it in `planApprovals`.

`approve-plan` transitions to `plan_verified`. A raw `transition --to plan_verified` cannot substitute for it. Execute preflight revalidates the receipt and baseline adoption. Replanning revokes the active receipt; a new audit and receipt are required.

## Task Checkpoints And Independent Verification

After entering `executing`, record each completed approved task with observed checks:

```bash
phasecraft runtime task-checkpoint --work PAY-142 --task T-001 \
  --checks '[{"name":"node --test test/payment.test.mjs","passed":true,"output":"14 passed"}]'
```

The runtime checks dependency completion, unchanged HEAD, and preservation of outside-scope work. It records the check results, completion sequence, implementation fingerprint, and a cumulative mode-0600 patch when approved files are changed. Repeating a task preserves its checkpoint history and invalidates dependent completions. All tasks must be checkpointed, and the final implementation must match the latest checkpoint, before execution completes.

Independent Verify supplies its own observed checks:

```bash
phasecraft runtime verification-result --work PAY-142 --outcome verified \
  --checks '[{"name":"independent regression checks","passed":true,"output":"passed"}]'
```

Use `verified_pending` with `--pending` for human-only checks and false check results with `verification_failed` for failures. Verification records bind the approval and implementation fingerprints. Pending check identities include their owning phase, so a later phase's `M-001` does not erase an earlier one.

## Ship Recovery

`ship-preview --work <id>` derives groups/messages from approved phases and checks/pending checks from recorded verification. It namespaces group identities by phase, merges overlaps, and includes only changed approved files. Supplied groups or check overrides must match those records.

Ship stores `ship/journal.json` before attempting commits and after each successful commit. The journal includes the original preview, approval contract, completed commit identities, and the pending group and parent. Recovery verifies parent, message, exact files, and binary diff. If a process stopped after committing but before writing its receipt, the pending commit can be reconciled from Git.

After an interruption:

```bash
phasecraft runtime resume --work PAY-142
phasecraft runtime ship-preview --work PAY-142
```

Preserve already recorded commits. Resolve any reported drift or hook failure. A failed hook may leave staged changes; unstage them without discarding their content before making a new preview. Approve the new fingerprint for remaining groups, including the separate pending-check acknowledgement when required. A completed journal allows the agent to finish `SHIP.md` and transition to `shipped` without creating duplicate commits.

## Read-Only Readiness

`doctor` and `resume` return JSON containing state/revision, approval validity, blockers and warnings, authority drift, completed/remaining tasks, last checkpoint, recorded Ship commits, pending manual checks, review availability, and unresolved HTML feedback with host-correct commands. They do not modify state or artifacts. `status` includes the same report under `readiness`.

## Upgrade Existing Work

Reinstall the chosen adapter, then restart OpenCode, Claude Code, or Codex; use `/reload` in Pi. Project configuration and existing artifacts remain in place.

Existing v0.4 work remains readable. An old `plan_verified` or later state without a runtime receipt cannot proceed through the new gates. Archive the audited plan, transition to `plan_draft`, rerun the audit with `approve-plan`, then checkpoint and independently verify the implementation. Existing implementation files may be retained; do not reinitialize the project or silently adopt baseline-dirty files. Later workflow states can return to `plan_draft` for this recovery. Already shipped work is historical and needs no migration.
